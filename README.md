# SEO Pipeline

A standalone Python 3.12+ application that collects multi-site SEO metrics and
produces a customer PDF, a private operator/LLM Markdown report, and versioned JSON.
It never reads or changes monitored website repositories, deploys websites, or
uses Cloudflare credentials.

```text
sites.yaml -> OpenSEO / GSC -> normalized SEO snapshot
  -> previous-period comparison -> deterministic trends and candidate scores
  -> optional OpenAI structured analysis -> customer PDF + private Markdown + JSON
```

## Local setup

```bash
python -m venv .venv
# Linux/macOS:
source .venv/bin/activate
# Windows PowerShell instead:
# .venv\Scripts\Activate.ps1
pip install '.[dev]'
```

WeasyPrint requires native Pango/font libraries. On Ubuntu/Debian:

```bash
sudo apt-get update
sudo apt-get install -y libpango-1.0-0 libpangoft2-1.0-0 libharfbuzz-subset0 fonts-dejavu-core
```

On Windows, install the native libraries using the
[WeasyPrint installation guide](https://doc.courtbouillon.org/weasyprint/stable/first_steps.html#installation).
Set `WEASYPRINT_DLL_DIRECTORIES` to the relevant native `bin` directory when needed.
On macOS, install Pango using your package manager. The PDF uses installed fonts
and embeds real text; it does not require JavaScript or fetch remote resources.

## Try the complete pipeline without credentials

From the repository root:

```bash
seo-pipeline report --site edwardscapes --provider mock --period 2026-07
seo-pipeline report --site all --provider mock --period 2026-07
```

Equivalent: `python -m seo_pipeline report --site all --provider mock --period 2026-07`.
`--dry-run` also forces mock collection and disables all external calls. Mock mode
never invokes OpenAI, even when API credentials exist in the environment.

Two packaged June/July fixtures demonstrate gains, declines, new/lost keywords,
zero/unknown-safe comparisons, weak CTR and changing page clicks. A first mock run
automatically seeds the previous month. Other requested months reuse these fixtures
(odd month: July; even month: June) with explicit synthetic-data labeling. This is
a demonstration, not live performance for the configured domains.

## Configure sites

The active `config/sites.yaml` contains only Edwardscapes (`edwardscapes.com`),
linked to its named OpenSEO project. Placeholder sites live only in test fixtures.

Edit `config/sites.yaml` to change the monitored sites. IDs and domains must be unique. Disabled sites are skipped.
Domains must be hostnames without a scheme or path. Unknown configuration fields
are rejected, including credentials and website repository/deployment settings.

```yaml
sites:
  - id: my-site
    name: My Company
    domain: example.com
    enabled: true
    openseo_project_id: your-existing-project-id
    gsc_enabled: true
    search:
      country: US
      location_code: 2840
      language: en
      device: desktop
      # gsc_country: usa  # optional; absent means all countries
    reporting:
      comparison_period: previous_month
    target_keywords: [example service]
    competitors: [example.net]
scoring:
  min_impressions: 500
  min_volume: 100
  low_ctr: 0.02
  medium: 30
  high: 60
max_keyword_rows: 500
max_gsc_rows: 10000
```

Set the provider's country-level `location_code` and `language` for your market;
`country` is its readable label. The default is US/English. Target keywords and
competitors retain operator context; they do not trigger additional paid research.
`low_ctr` is an optional operator heuristic, not a universal benchmark. Omit it or
set null to disable low-CTR detection. All scores include their contributing
components and thresholds. Position improvement is previous minus current.

## Production setup

1. Create or select each site's existing project in OpenSEO and copy its project ID.
2. Connect the matching Google Search Console property in OpenSEO if GSC is enabled.
3. In OpenSEO **Settings > API keys**, create a key for unattended execution.
4. Supply `OPENSEO_ACCESS_TOKEN` (or `OPENSEO_API_KEY`) and `OPENAI_API_KEY` through
   your shell, secret manager, or CI. `.env.example` documents the names; `.env`
   is not automatically loaded and must never be committed.
5. Optionally set `OPENAI_MODEL`; default is the requested `gpt-5.6`. The account
   must have access to that model or you must configure an available model that
   supports Responses Structured Outputs. Model failure retains factual reports.

```bash
seo-pipeline report --site all --provider openseo
seo-pipeline report --site my-site --provider openseo --period 2026-07
```

Use `--no-ai` for deterministic analysis only. OpenAI uses the official SDK,
Responses API, and a Pydantic output schema. Evidence references, direction and
candidate metadata are checked before use. Exact quantitative evidence is rendered
by application code, not generated by the model. Qualitative model text is labeled
for operator review and never inserted into the customer PDF. Customer summaries
are deterministic, so they work without OpenAI.

**Timing matters:** GSC uses the requested month. OpenSEO live estimates and ranks
are observations dated at collection time, not historical monthly totals. Normal
last-month reports collect both and clearly distinguish them. Older backfills
leave unavailable historical estimates blank. Prior live observations become
comparable after subsequent monthly runs. See [the verified provider contract](docs/provider-contract.md)
for field mappings, authentication, pagination, cost controls, and limitations.

## Outputs and storage

```text
output/<provider>/<domain>/<YYYY-MM>/
  seo-data.json
  seo-performance-report.pdf
  seo-opportunities.md
  seo-performance-report.html
data/snapshots/<provider>/<domain>/<YYYY-MM>/seo-data.json
data/raw/<site-id>/<collection-date>/<request-hash>.json
```

- **`seo-data.json`**: machine-readable source of truth, schema version `1.0`.
  Includes validated collection, provenance, period, deltas, sample completeness,
  evidence, scores, analysis status and limitations. Null means unavailable.
- **`seo-performance-report.pdf`**: customer-facing month-over-month metrics,
  keyword visibility/movement, landing pages, queries, backlinks and definitions.
  No prompts, debugging output, speculative recommendations, or internal work plan.
- **`seo-opportunities.md`**: private semantic Markdown with dates/sources,
  directional trends, gains/losses and structured scored candidates. It can be
  pasted into an LLM as evidence, with explicit separation of provider strings
  from instructions. It recommends investigations and never claims site defects.
- **HTML**: retained for convenient report inspection and print troubleshooting.

`--output-dir` and `--data-dir` change the roots. Provider namespaces prevent mock
history from contaminating real reports. Preserve `data/snapshots` between monthly
runs. Lookup requires the exact preceding complete calendar month, matching site
and search configuration. Missing production history is backfilled from GSC where
possible. Corrupt/mismatched snapshots fail rather than silently miscompare.
Files are written atomically individually. Run one writer per site/period; the
output directory is not a multi-file transaction. An unsuccessful rerun may retain
an older PDF beside newer factual JSON; use the nonzero exit code and JSON timestamp
to avoid distributing artifacts from a failed run.

## GitHub Actions / CI

The workflow in [`.github/workflows/seo-reports.yml`](.github/workflows/seo-reports.yml)
runs on the **5th of each month at 10:17 UTC**, reporting the last complete month.
It also supports **Actions > Monthly SEO reports > Run workflow**. Manual runs
default to `mock`; choose `openseo` for production. Leave `period` blank for the
last complete month, or enter `YYYY-MM`. Run from the default branch; other
branches are skipped to protect shared history. The workflow must be merged into
the default branch before the schedule and manual button become available.

Before production use, configure real sites/project IDs and add these repository
Actions secrets under **Settings > Secrets and variables > Actions**:

- `OPENSEO_ACCESS_TOKEN`: your OpenSEO API key.
- `OPENAI_API_KEY`: your OpenAI key.
- `REPORT_ARCHIVE_PASSPHRASE`: keep the existing strong random value (at least
  32 characters) for private snapshot history. It is not used for PDF downloads.

Optionally set the Actions **variable** `OPENAI_MODEL` (default `gpt-5.6`). Mock
runs require only the history passphrase and never call paid services.

The job installs Python 3.12 and native PDF dependencies, restores the newest
retained snapshot archive for the selected provider, then invokes the normal CLI:

```bash
pip install .
seo-pipeline report --site all --provider openseo
```

Download **seo-reports-openseo** (or **seo-reports-mock**) from the workflow
run's **Artifacts** section. GitHub downloads it as a normal ZIP containing the
PDF files, organized by provider/domain/month. Unzip it and open the PDFs directly;
there is no password, GPG file, or nested tar archive.

Private snapshot history is uploaded separately as **seo-state-openseo** or
**seo-state-mock**. Snapshot JSON includes internal evidence/analysis, so this
separate archive remains encrypted and is restored automatically on subsequent
runs using `REPORT_ARCHIVE_PASSPHRASE`. Keep that secret unchanged. You do not need
to download or decrypt the history artifact to open the PDFs.

The PDF artifact contains only PDFs; no Markdown, JSON, or raw provider responses
are included. The history archive contains only snapshots and retains the old
encrypted filename for compatibility with earlier runs. Existing encrypted
archives remain readable by the workflow; old PDF downloads are not retroactively
converted. Rerun the workflow to get the new plain PDF ZIP.

Artifacts expire after 90 days (or earlier if repository policy limits retention),
so download backups. Successful sites' PDFs and collected snapshots are still
uploaded when another site fails; check the run result.

The workflow uses read-only repository/API permissions and serializes runs so two
writers cannot overwrite history. It does not trigger on pushes or pull requests.
GitHub may delay scheduled runs; public-repository schedules can be disabled after
60 days without repository activity. See [GitHub's schedule documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
The standalone CLI does not depend on GitHub Actions. No website GitHub access,
Cloudflare token, or deployment credentials are required.

Exit codes: **0** reports generated (possibly partial data or deterministic AI
fallback); **1** at least one site failed; **2** invalid config/CLI/period. Other
sites continue after a failure. Inspect JSON warnings and `analysis_status` for
recoverable degradation. JSON logs contain site IDs and safe messages, not tokens.

## Tests

```bash
pytest -q
ruff check src tests
ruff format --check src tests
```

Tests use fake providers and SDK responses. External network is blocked (loopback
is allowed for Windows asyncio internals). PDF tests use actual WeasyPrint and
check extracted text, so native PDF libraries are required. Coverage includes
configuration, dates/year boundaries/leap years, arithmetic/zero denominators,
keyword movement/buckets/scoring, missing/truncated data, snapshot persistence,
HTML/Markdown/PDF, multi-site runs, failure isolation, auth errors, provider
mapping/cache/pagination and structured OpenAI validation.

## Troubleshooting

- **Missing/invalid OpenSEO credentials:** create an API key using the documented
  Settings page; supply it via the environment. OAuth token renewal is not
  implemented. Check project permissions and available provider credits.
- **GSC unavailable:** connect the exact property in the configured OpenSEO
  project; check its hostname, date range, recent data lag, and granted scopes.
- **Live estimates missing in old reports:** tools do not support historical
  dates. This is deliberate; no invented historical values are substituted.
- **Incomplete keyword sample:** increase `max_keyword_rows` (up to 1100), accepting
  possible credit costs. Absence in a partial sample is never labeled a loss.
- **Schema changes:** inspect the dated raw responses and update the isolated
  adapter against current OpenSEO documentation. Do not paste credentials into logs.
- **OpenAI unavailable/refusal/invalid evidence:** factual JSON and PDF still
  render, with deterministic candidates in Markdown. Check model access and key.
- **WeasyPrint import error:** install Pango and its dependencies; verify the DLL
  path on Windows. JSON survives PDF failures, and the CLI exits nonzero.
- **Configuration failure:** check YAML syntax, duplicate IDs/domains, unknown
  fields, numeric ranges, enabled site selection, and `YYYY-MM` formatting.

There are no website modification or deployment capabilities in this package.
